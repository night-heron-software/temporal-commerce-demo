## Addendum — 2026-08-18: mono #284 ported

One day after this ledger's baseline, the mono's first-ever live failed fulfillment (the #151
harness fail leg) exposed [mono #284](https://github.com/night-heron-software/nightheron-mono/issues/284):
`aggregateShippingState` counted `rejected` as delivered, so an ALL-rejected order aggregated to
`delivered`, stamped `deliveredAt`, and told the shopper it had arrived. **This graph carried the
identical `isDelivered = delivered || rejected` line**, so the fix is ported (mono PR #286): fifth
aggregate verdict `rejected` → new `FulfillmentRejected` event → `terminal('failed')` from all
three shipping states, new `OrderStatus 'failed'`, `deliveredAt` only on genuine delivery. The
mixed-order half of the old behaviour (one rejected line does not hold a delivered order back) is
kept and pinned by a CONTROL. Six tests (+ the event-table entry; union pin 22 → 23), fail-proved
the same way as upstream: reverting the all-rejected branch turns exactly the three #284 tests
red while both CONTROLs stay green. The mono's COGS half of the defect has no counterpart here
(no accounting domain).

Also: the "mono #282 HELD — unfinished upstream" row above is now stale upstream — #282 landed as
mono PR #283 (seed every discovered fulfiller). The demo remains single-fulfiller, so its
`seed-inventory` route stays a watch item, unchanged.

## Addendum — 2026-08-18: payment idempotency key diverges (attempt nonce, not amount)

The `${cartId}-${totalPrice}` key this ledger ported from mono `f42c3bda` (#241) is **replaced
in the demo** — a deliberate divergence, decided at plan review. The grounds: an amount is not
an identity (a same-total basket swap aliases to one key and rides the old charge); the refund
path (`prepareSubmitOrder`'s inventory-confirm failure) leaves a "charged" key that a same-total
retry dedupes against — with real gateway semantics, a free order; float-formatted money makes
unstable key strings; and folding a parameter into the key converts a conflicting replay (a bug
to surface) into a silent new charge.

The demo's shape is now the gateway model: the key is a nonce naming the ATTEMPT —
`${workflowId}-pay-${paymentAttempt}`, the checkout's own workflow id used whole (never parsed)
plus an ordinal in `CheckoutContext`. The `SubmitRejected` fold consumes the attempt when its
charge is settled (declined, refunded, never made) and RETAINS it when the pipeline failed with
a possible charge outstanding (`mayHaveCharged` on the prepared failure), so a retry replays the
key and reuses the charge. The mock now stores key → amount and throws a non-retryable
`IDEMPOTENCY_KEY_AMOUNT_MISMATCH` on a replayed key with a different amount. Scope change stated
plainly: the key no longer spans re-checkouts of one journey — cross-instance protection belongs
to the `paymentAlreadySucceeded`/`paidAmount` guards (the WATCH above), which this makes no less
mandatory the day real payments land.

**Backport candidate — flagged for the mono**, where the same aliasing ships against real
Stripe. Four key-shape property tests replace the three ported ones (fail-proved: restoring the
amount key turns exactly those four red), plus a mock-gateway contract suite
(`checkout/activities-impl.test.ts`). Tests 761 → 765 (+4 net: 4 reshaped, 3 gateway tests
added, and the count re-verified live at commit time).
