# Mono sync — 2026-08-10

Forward-port of the **CommandBlock sweep** (mono clarity-plan follow-through, PRs
#210–#221) from `nightheron-mono` (`main` @ `ae1848f`). Previous sync:
[2026-08-09](mono-sync-2026-08-09.md) (mono `a3cb60e`, framework `01ec172`), which landed
the decider-native surface itself; this sync brings the demo to the mono's **current**
convention rather than one behind.

The sweep is three moves applied to every machine, in one pass per domain (mirroring mono
#210/#211 for cart, #213 for checkout, #214 for oms, #219 for both fulfillment machines):

1. **Co-location** — each `<domain>-decider.ts` merges into its machine's states file
   (the fulfiller decider into `fulfiller-states.ts`); the decider files are deleted and
   every re-homed export keeps its name. The decider test FILES keep their names and
   retarget to the states modules.
2. **Structural purity** — the blanket deep-copy barriers (`copyCart`/`copyCtx`,
   `copyOrderState`, `copyState`, `draftCtx`) are DELETED; every evolve entry takes
   `Readonly` parameters and returns a NEW context built with spreads (structural
   sharing). Cart's mutating `cart-logic.ts` helpers were rewritten pure and merged into
   `cart/states.ts`; the file is deleted.
3. **CommandBlocks** — ONE exported `CommandBlock<K>` per command with
   guard / prepare / decide / evolve INLINED; shared multi-emitter evolve entries are
   named references; each machine's central `decide` dispatches over a mapped `blocks`
   table and its central `evolve` is ASSEMBLED by merging every block's evolve map,
   throwing at module load on divergent duplicates. The `m.state` commands tables
   reference the SAME blocks; registries, routes, and timeouts are unchanged. File-wide
   in every states file: `context` never `ctx`, `evolve` never `fold`.

## Intentional differences kept (do not "fix" in future syncs)

Carried forward from [2026-08-09](mono-sync-2026-08-09.md) — every divergence is
preserved, now re-expressed in pure/block form:

- **No Stripe / no Twisp ledger** — unchanged. *Block form:* no `ensurePaymentIntent`
  block (checkout keeps its mock `createPaymentIntent` in `prepareSetShipping`); OMS's
  `capturePaymentBlock` decides a bare `PaymentCaptured` with no capture payload and no
  ledger effect; `refundOrderBlock` keeps the demo's `computeRefundRecord` mock-refund
  math.
- **Reservations kept on payment failure** — unchanged; `prepareSubmitOrder` returns the
  failure without releasing (mono releases holds there). Still locked in by an untouched
  checkout `states.test.ts` case. Relatedly, the demo's `Cancelled` event still carries
  the **pre-evolve** reservation list (decided in `cancelCheckoutBlock` /
  `checkoutTimedOutBlock` from pre-evolve state; the shared `evolveCancelled` clears
  `context.reservations` so `onTerminal` cannot double-release; the machine-level effect
  releases exactly what the event carries).
- **Best-effort submit freeze** — unchanged; the try/catch `freeze` closure lives in
  `submitOrderBlock.prepare` (mono signals unconditionally).
- **Single store** — unchanged; `DEMO_STORE_ID` in `beginCheckoutBlock.prepare` and the
  OMS `startFulfillmentEffect`; plain numbers instead of `Money` throughout the blocks.
- **Cart** — no `mergeCarts` / `adoptCheckout` / `destroyCart` blocks (mono has them).
  Reservations remain per-variant release-then-re-reserve: `addItemBlock` /
  `updateQuantityBlock` prepare **compensate by re-reserving the old quantity before
  throwing** (not mono's ADR-0022 absolute sku holds); `linkUserBlock` carries
  `email` + `userId`; `respond: (context) => context.cart` (mono wraps `{ cart }`); the
  `checkoutCompletedBlock` evolve still clears `checkoutWorkflowId` on `CartCompleted`
  (the child already closed — mono keeps the link). The pure `addItem` keeps the demo's
  no-limit semantics (mono enforces MAX_ITEMS / MAX_QUANTITY and integer-cents prices).
- **Fulfiller child `submitted` command** — unchanged: `submittedBlock` keeps the
  `submitted`/`OrderSubmitted` pair with the submit call in its `prepare` (a failed
  submit throws → prepare-throw REJECTION → the state timer re-synthesizes the command:
  the visible retry loop). The **simulated tracking number stays derived from the
  workflow id** in `simulatedShipBlock.prepare` (mono derives from the timestamp in
  `evolve`). Timeouts stay **plain Durations** via `buildFulfillerOrderStates` (mono uses
  `(context) => Duration` strategy-descriptor resolvers). The parent `notifyParent` call
  stays in `onTransition`, and the `shipped → __terminal:failed` edge is kept.
- **OMS** — no return-window / SLA timers: no `checkReturnWindowBlock` /
  `checkReturnSlaBlock`, no `closed` status in `FORCEABLE_STATUSES`, no `OrderClosed`
  event. The `delivered` state keeps the demo's `guardDeliveredUpdateStatus` (layers the
  refund-selection check on the shared `guardForceableStatus`; mono's `delivered` uses
  the bare shared guard) under its literal `updateStatus` entry with the refund `enrich`.
  The sku fallback in the fulfillment hand-off (`a.sku || a.variantId` in
  `buildFulfillment`) is kept, as is `assignFulfillersBlock`'s `sku: assignment.sku`
  (mono prefers the order line's own sku first).
- **Identity** — unchanged (not a machine domain; not part of the sweep).
- **Layout** — the shared-contracts divergence carries forward: signal/query/update
  definitions live in `src/temporal/contracts/<domain>.ts` (mono: per-package
  `definitions.ts` + duplicated contracts), the command unions live there and the
  domains' `types.ts` re-export them; the framework stays vendored at
  `src/temporal/framework/`. The **per-domain decider-file split is erased**: the demo
  now matches the mono's co-located one-file-per-machine layout (this part's whole
  point), so the 08-09 note that the pure core lives in a separate
  `<domain>-decider.ts` no longer describes this repo. One residual demo-only wrinkle:
  `EnrichedCartCommand`-style unions and the `CommandBlock` interfaces are exported from
  the states files exactly as in mono, but the fulfiller machine also keeps its command
  union (`FulfillerOrderCommand`) in `fulfiller-states.ts` rather than a contracts file,
  as before.
